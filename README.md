# letxNepal

A national tourism platform for Nepal. Its purpose is to surface the country's hidden and
remote destinations and to grow tourism across all seven provinces — not only the classic
Pokhara, Kathmandu and Annapurna circuit.

## Status

Early build. The discovery layer (destinations, hidden gems, coverage reporting, public
API) is implemented and tested. Booking, the owner dashboard, the admin CMS and payments
are planned. See `docs/spec.md` for the feature table.

## What exists today

- **23 destinations** across all 7 provinces, 15 flagged as hidden gems, each with
  remoteness, access level, permit requirement, best season, nearest settlement, local
  community and households supported.
- **Discovery pages**: `/`, `/destinations`, `/destinations/hidden`,
  `/destinations/[slug]`, `/trails`, `/adventures`.
- **Coverage reporting**: `/coverage` and `/api/v1/regions/coverage` name every district
  that has no listed destination. 21 of 77 districts are covered; 56 are the measured
  backlog.
- **Public API v1**: `/api/v1/destinations`, `/api/v1/destinations/{slug}`,
  `/api/v1/regions/coverage`, `/api/v1/trails`, `/api/v1/health`.
- **Design system** generated by the `ui-ux-pro-max` skill, with token-integrity and WCAG
  contrast gates in CI.

```bash
npm run dev
```

## Tests

41 tests pass at the time of writing:

- 12 domain integrity — 7 provinces, 77 districts, every destination resolves, taxonomy
  values valid, coordinates inside Nepal's bounding box.
- 18 design tokens — every semantic role present, tokens.json and tokens.css agree, fonts
  are Devanagari-capable, all contrast pairs ≥ 4.5:1, no raw hex in components.
- 11 structural accessibility — document language, skip link, focus visibility,
  reduced motion, touch targets, base type, and every input has an accessible name.

## Architecture in one paragraph

Next.js 15 App Router with TypeScript end to end. Pages are Server Components; the public
API is Route Handlers. All input validation uses one Zod schema shared by the website
query string and the API, so the two cannot drift. Destination data is accessed only
through `src/lib/destinations/repository.ts`, which currently serves a curated static
dataset with the exact query semantics the Postgres implementation will use — the
storage layer can be swapped without touching the UI or the API.

See `docs/architecture.md` and `docs/adr/`.

## Design

The visual system is generated, not invented. `ui-ux-pro-max` produced
`design-system/letxnepal/MASTER.md`, `tokens.json` and `tokens.css`. Two recommendations
were overridden with reasons recorded: the font (the suggested family had no Devanagari
glyphs) and the motion (the product mandate is a very simple UI). Full detail in
`docs/provenance.md` and `docs/adr/0002-design-system.md`.

## Data honesty

Destination coordinates are approximate. 12 of the 23 seeded destinations are flagged
`coordinatesVerified: false`. They are for map placement and distance estimation only and
must be verified against an authoritative source before launch.
